# NDF 3 Test Files Creation

Creates a consistent, validator-passing set of files:
1. An **Input** GDB CSV (`Input_<category>_<subsidary_cd>_TestFile_<YYMMDD>[_<scenario_tag>].csv`)
2. A **Spec Grouping** xlsx (`SpecGrouping_<category>_<YYMMDD>_TestFile[_<scenario_tag>].xlsx`, sheets `specNameCommon` + `exception`)
3. A **Type Grouping** xlsx (`TypeGrouping_<category>_<YYMMDD>_TestFile[_<scenario_tag>].xlsx`, sheets `TypeMatch` + `BasicSpecDefenition`)
4. A **Test Scenarios** doc (`TestScenarios_<category>_<YYMMDD>_TestFile[_<scenario_tag>].md`) — maps the user story's requirements to the specific rows generated, not part of the pipeline upload.

5. **DDB mode only (on explicit request):** a **Discontinued** CSV (`Discontinued_<category>_<subsidary_cd>_TestFile_<YYMMDD>_<scenario_tag>.csv`) derived from the Input CSV — see "DDB mode" below and `test_run_conventions.md` §16.

The 3 pipeline files (1-3) are what actually gets uploaded to S3 and processed. The doc (4) is reference material for the person running the test — it doesn't go through the ETL pipeline and doesn't need to satisfy any pipeline validator.

Two reference files back this skill — **read both before generating anything**:
- `references/validation_rules.md` — full per-field validator rules (META/STRUCTURE/ROW/COLUMN/DATA layers) for all three registries, plus a cross-file consistency checklist.
- `references/test_run_conventions.md` — the Jira-ticket-driven conventions: how `category_name_common`, `part_number`, `part_number_type`, and file names are derived from a Jira ticket number, plus the required Input File columns and the S3 upload destination for each file.

These two docs govern different things (field-level validation vs. naming/derivation) and both apply simultaneously.

A scripts folder backs this skill so the mechanical, error-prone parts aren't redone by hand each time. See "Generation helper scripts" below.

## Generation helper scripts

- scripts/build_files.py: call build(...) with plain Python list-of-dict rows (CSV rows, specNameCommon rows, exception rows, TypeMatch rows, BasicSpecDefenition rows) plus the shared naming params. It writes the CSV with a verified UTF-8 BOM and both xlsx files with the exact required sheets, and derives all 3 file names from the naming convention. It raises immediately if exception_rows is non-empty, basic_spec_def_rows isn't 1-2 rows, or subsidary_cd is invalid. The same module also has `doc_filenames(...)` (derives the doc file name) and `write_doc(...)` (writes a markdown doc) for the Test Scenarios doc.
- scripts/build_files.py also has `parse_pipe_table(text, expected_header=None)`, scoped to **Input CSV rows only** (not specNameCommon/exception/TypeMatch/BasicSpecDefenition rows, which stay plain Python list-of-dict literals). It turns a compact pipe (`|`) delimited header+rows text block into the `input_rows`/`input_header` shape `build()` expects, saving tokens versus writing a Python dict literal per row — see step 4. The one authoring rule to remember: `part_number_rules` is the only column that's legitimately multi-line, so an embedded newline inside that cell must be written as the literal `\n` escape, not a real line break (`parse_pipe_table` converts it back after parsing).
- scripts/build_files.py also has `build_discontinued(input_rows, recommendations, category_name_common, subsidary_cd, yymmdd, scenario_tag, n_slots=3, output_dir=...)` for DDB mode. `recommendations` is an ordered dict `{ddb_part_number: [normal_part_number, ...]}` (an empty list means no alternative). Every other value is looked up from `input_rows` (params unchanged, `_en` columns taken from `*_original`), so nothing is retyped. It raises when a DDB row is missing or not in the GDB, a DDB row is recommended, a recommendation repeats, or a row has more recommendations than `n_slots`. `discontinued_filename(...)` derives the name, and the scenario tag is mandatory.
- scripts/validate_files.py <input_csv> <spec_xlsx> <type_xlsx> [<discontinued_csv>]: the optional 4th argument (DDB mode) also runs the Discontinued file checks from `validation_rules.md` §4. Run this on the generated output before calling present_files. It checks BOM presence, required/non-null columns, spacing/duplicate-row rules, enum values, spec_type/spec_value/params cross-checks, icon consecutiveness and cross-column icon consistency (including the selectable/derived split, ordering, and the +/- value restriction, §3a), part_number_rules line format (incl. AND/OR and derived-icon assignment/reachability, §8), and cross-file consistency rules. It prints ERROR/WARN lines and exits non-zero if any ERROR exists. It only checks the 3 pipeline files, not the doc (the doc is free-form markdown, nothing to validate structurally).
- Treat any ERROR as blocking: fix the underlying row data and rebuild. Surface any WARN to the user rather than silently deciding it is fine.
- These scripts only handle mechanics; they do not decide what data to generate or what the doc says. That is still driven by the ticket/story and the coverage checklist below.

## Workflow

1. **Read both reference files fully first.** Do not rely on memory of the source spreadsheets/docs — rules may have been updated.
2. **Get the Jira ticket number, and the user story / description.** Ask for both if not already given — the description informs realistic spec names, category context, brand/part details, and whether a scenario tag applies.
   - **If the user provides a Jira ticket URL**, try to read it directly rather than asking them to retype the details:
     - Check for a connected Jira MCP tool (scan available MCP servers/tools for one whose name/description handles Jira). If one exists, use it to fetch the ticket's summary, description, and ticket number directly.
     - If no Jira MCP tool is connected, try `web_fetch` on the URL — this only works if the ticket is reachable without authentication (most internal Jira instances are not, so this will often fail; don't retry repeatedly).
     - If neither works, tell the user their instance isn't reachable and ask them to paste the ticket number plus the story/description text directly.
   - **If the user just gives a ticket number** (e.g. "NDFDPAPJ-1761" or just "1761") with no URL, ask for the user story/description separately if they haven't shared it — don't fabricate it.
   - From the ticket number, derive per `test_run_conventions.md` §2–4:
     - `category_name_common` = `category_name_original` = `JIR A<first digit> <last 3 digits>` (ticket `1761` → `JIR A1 761`).
     - `part_number_type` per row: `JIRA-01`, `JIRA-02`, ... zero-padded, sequential, never skipping or reusing across tickets.
     - `part_number` per row: `JIRA-<ticket>-<NN>` plain, or `JIRA-<ticket>-<NN>-<icons>` when that row uses parameters — icons, `params`, and `part_number_rules` are all optional together (§3). Icon count varies row to row when present — don't assume a fixed icon count, and don't add icons/params/rules to rows that don't need them. Only *selectable* icons appear in this suffix — any *derived* icons for that row live only in `params` (§3a).
   - **Ask the user whether part numbers should be without icons, with icons, or a combination of both across the rows** — don't assume this. Options to offer: (a) all plain, no icons/params/rules anywhere; (b) all rows use icons/params; (c) a mix, some rows plain and some with icons (this is usually the most realistic and the default recommendation, since it exercises both code paths, but confirm rather than assuming). Whatever is chosen drives every row built in step 4.
   - **If icon-bearing rows are included, also ask whether any should include derived icons** (icons defined in `params` but auto-assigned via `part_number_rules` rather than appearing in the `part_number` suffix — §3a). Don't add derived icons unless the user wants that coverage; a row can be fully valid with selectable icons only.
   - Ask whether the request implies a specific test **scenario** (e.g. "test AND/OR rule logic") — if so, agree on a short scenario tag (§7 of `test_run_conventions.md`) to append to all 3 file names.
   - Use the story/description to choose sensible `spec_name_common` values, brand context, and any category-specific details that make the test data realistic rather than generic placeholders — but confirm your interpretation with the user rather than silently guessing at ambiguous requirements.
   - If no ticket number is given at all, ask for one — category/part-number derivation depends on it and shouldn't be guessed.
   - **DDB mode:** if the user says the ticket is for DDB (discontinued database) or asks for a Discontinued file, switch on DDB mode (see "DDB mode" below). The scenario tag becomes mandatory, because it is also the Discontinued file's 1-2 word test-nature suffix. Never enable DDB mode unless it has been asked for.
3. **Gather or assume the remaining shared parameters**, stating any assumption made:
   - `subsidary_cd` — one of `KOR`, `MJP`, `USA` only (see `test_run_conventions.md` §5; do not use `JPN`/`TWN`).
   - `brand_name_common` / `brand_name_original` (default `MISUMI` for test data per convention).
   - 1+ `spec_name_common` values (become the spec columns in the Input CSV; only 1–2 of these — and only ones present on **every** CSV row, not just most — will later go into `BasicSpecDefenition` — see §13 and step 6's compulsory rule).
   - the date to use in file names — `YYMMDD`, 6 digits (use the actual current date unless the user gives one).
4. **Decide the scenario/edge-case coverage plan before writing any rows.** By default, generate enough rows to exercise every structurally-distinct case the validators and conventions define — not just one minimal happy-path row per file. Walk the checklist below, decide which rows will cover which case, tag each row with which of the 4 data types it represents (see below), and confirm the plan with the user if the ticket/story doesn't make the intended coverage obvious (see "When to ask for feedback"). Then **build the Input CSV** — it is the source of truth the other two files reference. Merge the column requirements from both reference docs (the Jira-derived columns like `part_number`, `part_number_type`, plus the full validator-required set: spec_type_1..N, params, part_number_rules, economy_flag, etc). `cad_url`, `image_alt`, and `image_pass` columns must exist in the header but stay empty for every row (§14).

   **Author the row data as a pipe-delimited text block, not a Python list of dicts** — this is what generates the actual token savings. One header line (column names joined by `|`, defining `input_header`), then one line per row with values in the same order, also joined by `|`. Rules:
   - Empty cells are just two consecutive `|`s — no placeholder text.
   - Every row line must have exactly as many `|`-separated cells as the header — pad trailing empty cells for rows using fewer spec sets than the widest row in the file.
   - Never put a literal `|` inside any cell's content.
   - `part_number_rules` is the one column that's legitimately multi-line (one `IF [...] Rule ...;` statement per line, §8). Encode an embedded newline inside that cell as the literal two-character escape `\n`, not a real line break.
   Parse the block with `scripts/build_files.py`'s `parse_pipe_table(text)` to get `input_rows`/`input_header` before step 9.

   **The 4 data types to generate** (every row belongs to one of these; track which is which so the Test Scenarios doc in step 12 can reference them):
   - **Happy path** — straightforward, realistic values that clearly satisfy every rule with no ambiguity. The baseline majority of rows.
   - **Boundary values** — values sitting exactly at or just inside a limit the rules define: e.g. a `range` param row using `min` and `max` themselves (not a comfortable mid-range number), the minimum valid `step`, the shortest/longest realistic string a field allows, the first (`①`) and last icon in a parameter sequence.
   - **Invalid data** — values representing a genuinely invalid/unmapped/non-matching *business* case, while still being fully schema- and rules-compliant (this is not the same as a deliberately broken row that fails a validator — see Notes for that separate, opt-in case). The `XYZ=XYZ` catch-all pattern (§10) is the standing example: a value that doesn't satisfy any named rule condition, used to test the negative path, but still valid CSV/xlsx data. Only include this type where it's actually needed to exercise a negative path the ticket cares about — don't add invalid-data rows just to check a box.
   - **Edge cases** — structurally unusual but valid combinations: the maximum icon count used elsewhere in the file appearing on one row and a single icon on another, a row with the maximum number of spec sets alongside one with just the minimum, an `IF` condition chaining several `AND`/`OR` terms rather than one, multi-byte/non-ASCII text in `spec_name_original_*`.

   **Coverage checklist** (include a row for each applicable case, tagged with a data type above; skip only what's genuinely inapplicable to the ticket, and say which you skipped and why):
   - **Part number shape**: follow whatever the user chose in step 2 (no-icon / with-icon / mixed). **A row whose `part_number` has no icon must have an empty `params` column** — never leave a stray params block on a plain part number, since there's no icon for it to define anything against. Conversely, every icon that does appear in `part_number` must have a matching entry in `params` (§3 of `test_run_conventions.md`) — though `params` may define additional *derived* icons beyond that, if the user opted into that coverage (§3a). If a mix was chosen, include at least one fully plain row and at least one icon-bearing row so both shapes are represented.
   - **Derived icon coverage** (edge case, only if the user opted in during step 2): at least one row where `params` defines a derived icon (numbered right after the row's selectable icons, listed after them in the `params` cell) whose values are auto-assigned via `part_number_rules` branches. Make sure every value defined for that derived icon is actually reachable by some branch (§3a/§8 of `test_run_conventions.md`), and that none of its values are copied onto a selectable icon (selectable icon values must never contain `+`/`-`).
   - **spec_type coverage**: at least one row exercising each of `fixed`, `irregular`, `range`, `formula` that's relevant to the ticket — each has distinct spec_value/params cross-check rules in `validation_rules.md` §1, so a set that only uses `fixed` doesn't exercise the other three validators at all.
   - **params shapes**: an irregular-type params block with an explicit value list (remember the `XYZ=XYZ` catch-all per §10 — invalid-data type), and a range-type params block with a valid `min-max/step`, plus a boundary-value row using the range's own min/max.
   - **part_number_rules logic**: at least one row with a `Rule`-only line, and — if the ticket concerns rule logic at all — rows exercising `IF [...]` conditions with `AND`, with `OR`, and combinations of both in either the condition or the consequent (§8 of `test_run_conventions.md`, edge-case type). This is usually the highest-value coverage area for tickets like JIRA-1761 that are specifically about rule matching. If any row includes a derived icon, its `part_number_rules` must assign every value that icon's `params` block defines — no defined value left unreachable (§8).
   - **Multiple spec sets**: at least one row with 2+ spec_type/spec_value/spec_unit sets (N=1, N=2, ...), not just the minimum required N=1.
   - **economy_flag**: both `0` and `1` represented somewhere in the file.
   - **Icon count variation**: if any rows use icons, don't use the same icon count on every parameterized row — vary it so icon-consecutiveness checks run against more than one shape (edge-case type).
   - **Non-ASCII data**: include Japanese (or other non-ASCII) text in at least one `spec_name_original_*` value so the UTF-8 BOM requirement (§15) is actually exercised, not just theoretically satisfied by all-ASCII data.
   - **Uniqueness**: 2+ distinct rows minimum so duplicate-row and cross-field uniqueness rules have something to check against.
   - Everything above — happy path, boundary, invalid-data, and edge-case rows alike — must still fully satisfy every validator in `validation_rules.md`. None of these 4 types means "let the file fail validation." Only add a genuinely validator-breaking row if the user explicitly asks to test specific validator failures (see Notes) — that is a separate, opt-in case from the 4 types above.

   Within all of this, satisfy every DATA/ROW rule in `validation_rules.md` (icon sequencing when icons are used, part_number_rules format with optional `IF [...]` + mandatory `Rule ...;` when rules are used, no forbidden characters, etc; never use `choice` as a spec_type — it is not a valid value).
5. **Build the Spec Grouping xlsx**, reusing the exact `category_name_common`/`subsidary_cd`/`spec_name_common` values from step 4. Populate `specNameCommon` with correct headers and non-null required fields, keeping `priority_order` and `spec_name_common` unique; the `calculationFormula` column defaults to empty, and if a row does populate it, the value must follow one of the 5 permitted syntax patterns in `references/validation_rules.md` §2 ("calculationFormula syntax rules") exactly — terminating `;`, correct spacing around `RULE`/`AND`/`OR`, only the allowed operator set, `±` only in the tolerance-range pattern (§14). The `exception` sheet must exist with its exact header — `#, subsidary_cd, part_number_type, brand_name_common, category_name_common, spec_name_common, stringReplacement, calculationFormula, unitConversionFormula` — but always has **zero data rows** — never populate it (§14).
6. **Build the Type Grouping xlsx**:
   - `TypeMatch` — one row per **every** `part_number_type` from the Input CSV, 1:1, no filtering. Reuse `category_name_common`/`subsidary_cd`/`part_number_type` from the CSV, but use **one single fixed "primary" brand** (typically `MISUMI`) for `brand_name_common` across every row, even if the CSV itself mixes brands per row — do not mirror each row's actual brand (§12 of `test_run_conventions.md`). Keep (`part_number_type`, `brand_name_common`) unique.
   - `BasicSpecDefenition` — a deliberately minimal matching-logic hint list of just **1–2 `spec_name_common` values**, preferably one(s) common across all part numbers, per §13 of `test_run_conventions.md`. Do not try to list every spec, and don't feel obligated to list every spec that happens to be common to all rows either — pick just 1–2. Keep `spec_name_common` unique within the sheet. **Compulsory rule: whichever `spec_name_common` value(s) you put in `BasicSpecDefenition`, every single row of the Input CSV must carry that spec_name_common in one of its spec_type/spec_name/spec_value sets — no exceptions.** This means the 1–2 values chosen here directly constrain step 4: pick `BasicSpecDefenition` values only from spec_name_common values that already appear on 100% of the CSV rows, not just "most" or "common" rows. If no single spec_name_common is present on every CSV row, you cannot populate `BasicSpecDefenition` yet — go back and either add that spec to the missing rows or choose a different spec_name_common that genuinely is universal, before building this sheet.
7. **Self-check against the cross-file consistency checklist** in `validation_rules.md`, plus the `TypeMatch`-is-complete-with-fixed-brand / `BasicSpecDefenition`-is-1-to-2-specs distinction above — cross-file mismatches and an over-populated `BasicSpecDefenition` are the most common failure modes. Also re-verify the `BasicSpecDefenition` universality rule from step 6: for every `spec_name_common` listed in `BasicSpecDefenition`, confirm every row in the Input CSV actually has that spec_name_common present. If any CSV row is missing it, this is a blocking inconsistency — fix it before proceeding, don't just flag it as a WARN.
8. **Name the files using the convention in `test_run_conventions.md` §6**, not the generic pattern in `validation_rules.md`, whenever the request is tied to a Jira ticket / real ETL test run (the default case for this skill):
   - `Input_<category_name_common_with_underscores>_<subsidary_cd>_TestFile_<YYMMDD>[_<scenario_tag>].csv`
   - `SpecGrouping_<category_name_common_with_underscores>_<YYMMDD>_TestFile[_<scenario_tag>].xlsx`
   - `TypeGrouping_<category_name_common_with_underscores>_<YYMMDD>_TestFile[_<scenario_tag>].xlsx`
   Always include `TestFile` in the name, use the 6-digit `YYMMDD` date, append the scenario tag identically to all 3 files if one applies, and get the pattern exact — the pipeline fails silently on a mismatch. **Preserve exact case and underscore-joining** (e.g. `Input_JIR_A1_457_KOR_TestFile_260721.csv`) — never lowercase the name, never join with spaces, and always use the subsidiary code actually confirmed for this run rather than a default/guessed one. Double-check the rendered file name against this pattern before saving; getting case, separators, or the subsidiary code wrong here is a known failure mode.
9. **Build the files with `scripts/build_files.py`** rather than hand-writing csv/openpyxl code — pass it the row-dicts assembled in steps 4-6 and the naming params from step 3/8. If Input CSV rows were authored as a pipe-delimited block per step 4, call `parse_pipe_table()` first to get `input_rows`/`input_header`, then pass those into `build()` exactly as you would a hand-written list of dicts. It handles the BOM and sheet/header mechanics and verifies the BOM itself. (If a case genuinely needs something the script can't express, fall back to the `xlsx` skill at `/mnt/skills/public/xlsx/SKILL.md` for that piece, but prefer the script by default.)
10. **Run `scripts/validate_files.py`** on the 3 generated files (in DDB mode, pass the Discontinued CSV as a 4th argument). Fix any `ERROR` and rebuild before proceeding. For any `WARN`, either resolve it or explicitly mention it to the user in your final message — don't silently dismiss it.
11. **Write the Test Scenarios doc.** Use `scripts/build_files.doc_filenames(...)` for the file name, then `write_doc(...)` to save it. Content rules:
    - Structure it as a simple table or list: **user story requirement → which row(s)/part_number(s) cover it → which of the 4 data types (happy path / boundary / invalid / edge case) it is → what it proves**.
    - Every requirement explicitly called out in the ticket's user story/description must appear here mapped to at least one row — this is what makes "did the generated data actually cover the story" checkable rather than a claim.
    - Include the general coverage-checklist items from step 4 too (spec_type variety, AND/OR logic, etc.), not only story-specific ones, so the doc is a complete map of *why* each unusual row exists.
    - Keep entries short — a row of a table, not a paragraph.
12. Save all files to `/mnt/user-data/outputs/` with the exact names from steps 8/11, then call `present_files` with all 4 paths together (3 pipeline files + the doc). In your final message, remind the user of each pipeline file's upload destination in S3 Explorer (Input → `gdb_registration`, Spec Grouping → `normalisation_master`, Type Grouping → `requirement_master`), and note that the doc is reference-only and doesn't get uploaded. In DDB mode, present the Discontinued CSV as well (5 files in total). Say that its S3 upload destination is "discontinued_db_registration/".

## DDB mode (Discontinued file, on request only)

Full convention: `test_run_conventions.md` §16; validator rules: `validation_rules.md` §4. This mode changes the normal workflow in these places:

- **Step 4, Input CSV:** 10 rows by default, 4 DDB and 6 normal, numbered `NN = 01..10` with the DDB rows mixed in. A DDB row's `part_number` is `JIRA-DDB-<ticket>-<NN>`, plus the icon suffix when it has params. `part_number_type` stays `JIRA-<NN>` on every row. DDB rows are ordinary GDB rows and must meet every coverage and validator rule above. Among the DDB rows include at least 1 plain and 2 icon-bearing rows, and keep at least 3 normal rows. Normal rows may be plain or icon-bearing.
- **Step 6, TypeMatch:** lists all 10 types, DDB rows included.
- **After step 9, build the Discontinued file** with `build_discontinued(...)` from the same `input_rows`. Default shapes for the 4 DDB rows: Plain → no recommendations; Plain → 1; Icon → 2; Icon → 3. N defaults to 3, giving 19 columns. Reuse at least one normal part number across two DDB rows. Each recommendation must be a normal row. `recommend_params_n` is copied from that row, so it is empty when the row is plain, and that is valid.
- **Step 11, doc:** add a table mapping each DDB part number → plain/icon-bearing → shape (0/1/2/3 recommendations) → recommended part numbers.
- Icons in the Discontinued file keep the GDB format `-①-②`, because values are copied from the GDB.

## When to ask for feedback

Ask the user rather than guessing when:
- The ticket/story doesn't make clear which of the coverage-checklist cases (step 4) actually apply — e.g. it's ambiguous whether rule-logic AND/OR needs exercising, or how many distinct spec_types are relevant.
- A coverage case would require deviating from a documented default (e.g. `BasicSpecDefenition` needing more than 1-2 specs, or the `exception` sheet needing real data) — these defaults exist for a reason and shouldn't be silently overridden.
- `scripts/validate_files.py` reports a `WARN` whose correct resolution isn't obvious from the reference docs.
- The user's request implies more files, different registries, or a full pass/fail permutation matrix per validator (JIRA-1761-style test *case* generation, as opposed to test *files*) — this skill's default scope is exactly 3 files, one comprehensive-but-valid example set per registry, tied to a single Jira ticket. Point them at the separate test-case-creation skill if that's really what they want.
- Any reference-doc rule seems to conflict with what the ticket is asking for.
- In DDB mode: when the user wants more than 3 recommendations (N > 3), a split other than 4 DDB / 6 normal, or shapes other than the default 0/1/2/3. Confirm the new layout before building.

Don't ask about things the workflow already has a documented default for (subsidiary code enum, brand default, always-empty fields, `BasicSpecDefenition` size, `TypeMatch` fixed-brand rule) — apply the default and state the assumption instead.

## Notes
- These are meant to be **valid, passing** files by default — comprehensive across the coverage checklist in step 4, not just a single minimal happy-path row — unless the user asks for deliberately invalid/edge-case rows to test specific validator *failures*. In that case, keep the 3 files cross-consistent but clearly call out in the final message which cells were intentionally made invalid and which validator each is meant to trigger.
- If the user's request implies more files, different registries, or many pass/fail permutations per validator (like JIRA-1761-style test case matrices), check with them — this skill's default scope is exactly 3 files, one comprehensive valid example set per registry, tied to a single Jira ticket.
- **The generated test data should cover everything called out in the ticket's user story/description**, in addition to the general coverage checklist in step 4 — if the description mentions specific scenarios, spec types, or edge conditions to exercise, make sure the rows you generate actually exercise them, not just a generic/minimal example. If it's unclear whether the data covers a described requirement, ask rather than guess (see "When to ask for feedback").
